What this is. The product's strongest proof is that the same policy, the same permission and the same files produce a different decision when one fact changes. Night A (the hero): the venue's letter only confirms the Thursday event, so at 00:38 the agent cannot verify that the venue can receive the van, and it wakes the owner. Night B: the venue's letter also says "Deliveries accepted Wednesday 08:00-16:00"; the agent finds that line, places the permitted hold itself, and lets the owner sleep. A visitor must be able to run Night B live, fresh from 21:30, on their own copy, and compare it with Night A.

Part 1. The control. On the front door, under the 00:47 question's buttons, a quiet second action "Change one fact instead". It opens one line showing the venue letter's sentence as it is in Night A, with the changed sentence for Night B beside it ("Deliveries accepted Wednesday 08:00-16:00"), and one button "Run the night with this fact". It starts a FRESH night on a new copy of the job (new job id, from 21:30, no reasoning replayed from any earlier run) with only that fixture line changed, using the existing case-override mechanism (the venue override from the matching eval case), the same policy and model configuration as the hero, and the supervision arm. The night runs compressed and streams its steps to the visitor exactly like the live answer path does (each real step as it is logged, with elapsed seconds; no spinner; no step shown before it happened). It ends on that copy's own morning page with its job id and raw event log link. It counts against the same daily spend cap and the same 2-concurrent-resume semaphore (a fresh night is one slot). When the cap is reached, show the recorded Night B instead with the one-line notice already used for the answer path.
