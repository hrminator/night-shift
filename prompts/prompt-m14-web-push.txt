What this is. The night's notify step (the moment the model's ask_owner is accepted and the owner is notified) can deliver a real Web Push notification from night-shift-demo.fly.dev to the owner's own phone, for the owner's own job only. Visitor jobs (copies made from the front door's answer step) stay simulated exactly as today: no push, the simulated notification event as before. This exists so the Saturday real-time test night can push to the owner's phone through the product's own notify step, and it is disclosed as such.

Part 1. Keys and config. Use the pywebpush library (add it as a dependency with uv) and VAPID. Add scripts/make_vapid.py that generates a VAPID key pair and prints the public key and the private key ONCE to the terminal for the operator to store; nothing is written to the repo. Config via environment: VAPID_PUBLIC_KEY, VAPID_PRIVATE_KEY, VAPID_SUBJECT (a mailto: or https: URL; default mailto:owner@example.invalid), PUSH_ENABLED (default off; push is skipped and logged as `push_skipped` {reason:"disabled"} when off or when keys are missing). Document all of them in DEPLOY.md without values. Never print key values anywhere else.

Part 2. Subscribing the owner's phone. A page GET /owner/phone that requires the X-Run-Token header or a ?token= query equal to RUN_TOKEN (otherwise 403, and the token is never echoed): it registers a service worker (static/sw.js), asks for notification permission, subscribes with the VAPID public key and POSTs the subscription to /owner/phone/subscribe (same token rule). Store subscriptions in a new table (id, endpoint, keys json, created_at, label). Only one owner; keep every subscription and send to all (a phone may re-subscribe). The page shows "This phone is subscribed as the owner's phone" and a "Send test push" button that calls POST /owner/phone/test (token rule) and sends a push titled "Night Shift test" with the current UTC time. The service worker shows the notification with title, body and a URL to open on tap; it never does anything else.

Part 3. The notify step. Jobs get a flag `owner_job` (default false). A job started by the operator through POST /jobs/run gets owner_job=true; visitor copies and eval runs never do. In the notify step, when owner_job is true and PUSH_ENABLED is on and at least one subscription exists: send one push per subscription with title "Night Shift", body = the first 120 characters of the model's question, and the URL of the job's answer page (the existing route for answering an open question; if it is token-guarded, include the token in the URL only for owner jobs, nowhere else). Log `push_sent` {subscription_id, status_code, seconds} or `push_failed` {subscription_id, error} per subscription; a 404 or 410 from the push service marks that subscription dead (column) so it is skipped next time. The simulated notification event is still written exactly as before, so scoring is unchanged. A push failure never fails the night. The morning page, when owner_job is true, shows one line under the notification: "Delivered by web push to the owner's phone at HH:MM" or "Web push failed" with nothing more.

Part 4. Operator command. scripts/send_test_push.py --title --body sends to every live subscription through the same code path as the notify step and prints status codes. It reads the keys from the environment and must work against the local DATA_DIR and, with --remote, against the live app through POST /owner/phone/test with RUN_TOKEN from the environment (so the test push on Thursday can be sent from the PC to the phone subscribed on the deployed site).
